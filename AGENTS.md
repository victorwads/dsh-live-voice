# DSH Live Voice agent guide

This is an information router. Read the relevant local `AGENTS.md` and `ARCHITECTURE.md` before changing code; consult [the architecture map](docs/ARCHITECTURE.md) and [voice lifecycle](docs/VOICE-LIFECYCLE.md) for contracts.

- Start with `README.md`, `HISTORY.md`, and `packages/live-voice/package.json` before project changes. `package.json` is the sole source for the plugin version and tested DSH version.
- Application integration, routes, slots, and i18n: [app guidance](packages/live-voice/src/app/AGENTS.md) and [architecture](packages/live-voice/src/app/ARCHITECTURE.md).
- Product behavior and provider adapters: [module guidance](packages/live-voice/src/modules/AGENTS.md); then the local architecture file in [core](packages/live-voice/src/modules/core/ARCHITECTURE.md), [conversation](packages/live-voice/src/modules/conversation/ARCHITECTURE.md), [settings](packages/live-voice/src/modules/settings/ARCHITECTURE.md), [recognition](packages/live-voice/src/modules/recognition/ARCHITECTURE.md), or [speaking](packages/live-voice/src/modules/speak/ARCHITECTURE.md).
- Reusable UI: [shared architecture](packages/live-voice/src/shared/ARCHITECTURE.md). Native local engine work also consults `.local-voice/qwen3-asr-swift/AGENTS.md` when inside that subtree.

## Repository-wide constraints

- Order applicable changelog release sections as `Features`, `Improvements`, `Fixes`, then `Developer notes`; omit empty or irrelevant sections. Release notes must describe user-facing changes or significant information contributors need to act on (such as breaking APIs, migrations, or changed tooling requirements). Do not include routine project maintenance, version bumps or package-version alignment, ordinary test additions or passing checks, build regeneration, or compliance with existing project standards. These are baseline project practices, not release deliverables. Include `Developer notes` only when there is a meaningful contributor-facing change, never as a technical work log or boilerplate. Do not add a feature/release highlight section or introductory highlight summary unless the user explicitly requests one for that release. Classify changes relative to the previous published version: fixes made while developing a new, unreleased feature belong to that feature, not a separate release fix. Preserve historical release entries unless explicitly asked to revise them.
- Keep English as the canonical language for documentation, comments, and public metadata. Keep the principal README discovery keywords visible in English, Brazilian Portuguese, and Simplified Chinese. Maintain `README.pt.md` as a Brazilian Portuguese translation with reciprocal links to the English original. Keep both READMEs aligned when changing product guidance. Maintain a single English `CHANGELOG.md`; do not create translated release histories. Lead public READMEs and release summaries with user benefits and use cases, moving implementation details to technical guides or clearly labeled technical sections. Internationalize all visible plugin copy, help, status, errors, tooltips, aria labels, and test phrases in every typed locale catalog. Keep translation keys descriptive and alphabetized; use the DSH `ctx.locale` service and keep UI language independent of STT/TTS languages and user-defined commands.
- Keep Settings compact: explanations, usage instructions, and descriptive help MUST use the shared accessible `Hint` tooltip, never permanent paragraphs or repeated helper lines. Consolidate help shared by a section into one tooltip beside its heading. Keep control labels, values, and actionable runtime/status/error feedback visible; do not hide failures in tooltips.
- Lead with local-first STT and TTS without claiming DSH itself is fully offline. Preserve separate capture/recognition, synthesis/playback, and generation states; distinguish pause, resume, and cancel. Avoid raw audio/transcript logging by default. Never infer capabilities from OS alone.
- `HISTORY.md` is an append-only human story, not a technical work log. Read it before a maintainer-requested story addition; never add a routine technical chapter or invent experiences. Keep acknowledgments in the README.
- Inspect real DSH extension APIs before altering integration. Do not fabricate hooks, manifests, support claims, or add features/dependencies merely to make a placeholder look complete. Check third-party engine and model licensing/platform requirements.
- Run `npm test` (which builds the client) and report fake-engine/DOM results separately from physical-microphone and authenticated-runtime validation. A packaging dry run is not a runtime test. Keep README's tested-DSH badge aligned if that version changes, and review generated bundle changes locally. Generated files under `packages/*/lib/` are ignored build outputs; never stage, commit, or push them, including during npm publication. Publish compiled runtime bundles through npm, not Git. Regular CI and pre-push checks validate source/build/tests; `npm run check:dist` belongs exclusively to release/publication validation and verifies the built npm package contents without requiring tracked bundles.
- Do not commit, push, publish, or create a secondary package without explicit authorization for this work. Prerelease publication requires explicit `--tag developing`; `npm publish --dry-run --tag developing` only checks packaging.
