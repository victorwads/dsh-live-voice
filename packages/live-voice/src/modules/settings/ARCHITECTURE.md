# Settings module

`services/pluginUpdate.ts` owns an application-lifetime explicit update state machine, passed into Settings by the app composition root. Opening Settings only checks GitHub; Update now reads profile eligibility, then requires a separate exact-version confirmation before the official DSH manager installs. Development/custom sources are never replaced; uncertain outcomes lock retries until the person checks the manager. Closing Settings preserves operation state. Installation never grants build-script permissions or restarts/reloads automatically. The inspected DSH manager returns restart-required for existing profile dependencies, so the running plugin is not replaced during download. Voice activity is checked immediately before submission, not reserved across the download or across browser clients. The manager offers no expected-source/CAS option: do not change this dependency through another manager/CLI concurrently with confirmation. Source is rechecked at confirmation but cannot be atomically guarded by this client.

`components/LiveVoiceSettings.tsx` owns the tabbed Settings shell; `sections/{conversation,recognition,speak}` own feature controls. `hooks/useLiveVoiceSettings.ts` subscribes to controller state and dispatches updates, while `hooks/useAudioDevices.ts` and `hooks/useReleaseStatus.ts` handle capability-adjacent data. `models/settingsStorage.ts` owns the authenticated client transport and in-memory preferences; `models/settingsHost.ts` owns serialized, atomic host-side persistence; `services/releases.ts` supports version metadata. Shared fields, layout, icons, and feedback live in `src/shared/design-system`.

Engine choice is configuration, not operational validation: every STT/TTS option stays selectable without provider health requests. Configuration load/save uses only the authenticated preference/config routes; explicit Test or start/play performs operational validation. Shared `core/engineSelection.ts` determines display order and new host preference defaults from authenticated host-platform metadata, never inferring actual support or overwriting valid saved choices. UI discovery refreshes only local voices, capture metadata, and playback-control mechanics.

`models/browserVoiceSelection.ts` owns pure Browser voice ranking and explicit engine-transition defaults. Rank available local voices by the Natural name label, client browser language family, then alphabetical name; this label is a preference hint, not a capability or quality guarantee. UI translation locale and host OS do not select speech language. Only an explicit transition to Browser preselects a discovered Natural voice. Empty discovery keeps the existing preference; subsequent asynchronous capability refreshes re-rank options without retroactively selecting a voice or overwriting manual choices. The selector groups voices by language family using native optgroups, with the browser language first, other languages alphabetically, and unknown language last; within each section Natural voices precede alphabetical names. The preferred Natural voice keeps a localized default suffix independent of the currently selected voice. Grouping does not change transition-default policy. No speech-language setting is changed.

Preserve existing setting names, default values, handlers, and normalization in `../core/settings.ts`; reorganizing presentation must not silently change policy. Keep transient capability/permission messages visible even when an options section is collapsed. User-facing copy and accessible names belong in all typed catalogs under `src/app/client/i18n`; UI locale does not select recognition or speech language. The preview in `__previewjs__/LiveVoicePreviews.tsx` exercises presentation with a fake controller, not a physical microphone or authenticated DSH runtime. Run `npm test` after changes and check the preview for layout and interaction.
